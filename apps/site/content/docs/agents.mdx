This is a technical reference for an agent that can execute local commands, or
for an advanced user who needs to supply those instructions directly to an
agent. For normal installation and first use, start with [Agent integration](./agent-setup).
The [Markdown version](./agents.md) can be supplied directly to the agent.

## Set up the environment

Check `lore --version` in your command environment. If unavailable, follow [Installation](./installation), keeping the complete release directory intact.

Use the installer that matches the host where the agent runs commands. macOS on Apple Silicon and Linux x64 use the Unix installer:

```sh
curl -fsSL https://raw.githubusercontent.com/lorelum/lorelum/main/install.sh | sh -s -- --version 0.1.0-alpha.2
```

Windows x64 uses PowerShell:

```powershell
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/lorelum/lorelum/main/install.ps1))) -Version 0.1.0-alpha.2
```

Do not run `install.sh` or double-click the installer on Windows. Run the PowerShell command from an already-open session so errors remain visible. macOS is the priority and most thoroughly validated release target; Linux and Windows are best-effort targets. Read [Installation](./installation) before treating another environment as compatible.

Inspect the installed CLI and Packs:

```sh
lore describe
lore pack list --details
```

Install the requested Pack if it is missing. To start with the official engineering Pack:

```sh
lore pack install agentic-coding
```

Follow [Agent integration](./agent-setup) for the current host. Codex and ZCode use their respective [official Plugins](./agent-setup); verify setup with a query about the current repository and a full Practice read.

If using a custom `--store-root`, use it consistently for install, query, get, and index operations. It chooses Pack and index data, not a different model or Backend.

## Retrieve when a judgment needs guidance

Useful moments include defining scope, deciding implementation boundaries, choosing verification, recovering context, and preparing a completion claim.

Describe the concrete task and moment:

```sh
lore query "I am implementing account settings. Focused component tests pass, and I am about to declare the whole feature complete."
```

Do not treat a Pack catalog as full guidance or a complete inventory of relevant knowledge. Query when it helps the decision; avoid mechanical retrieval before every command.

## Read and apply

Select results using their `title` and `appliesWhen`, then read the full body:

```sh
lore get <practice-id>
```

Use the exact `practiceId` from the query or Pack listing. Check applicability against the current code and user request. A Practice helps engineering judgment; it does not authorize new scope or replace evidence of completion.

Retrieve again if new facts change the decision. Describe how the relevant guidance affects the work without claiming that unrelated Practices were applied.

### Use linked Pack resources on demand

A Practice can link Pack-native material with a `resource:` target, such as `resource:references/api-compatibility.md`. Resolve it from the matching source's `packRoot` in the `get` result. Read a reference when it provides the extra detail needed for the decision; copy an asset into the task workspace before editing it; and run a script only when the current task authorizes it and the Practice explains its inputs and purpose.

The link is the default task route, not a file-access allowlist. A SessionStart Catalog injected by the Codex or ZCode Plugin gives every installed Pack its readable current `packRoot`, so you may use that root when the Pack context is already clear. For a retrieved Practice, keep multiple sources separate and use the matching `get` source root rather than silently choosing a Catalog entry. A root is a mutable current view: after a Pack mutation, retrieve `get` or `pack list` again before treating it as the current source; never derive roots from Store internals. Never assume a Pack script runs during install, validation, query, listing, get, indexing, or recovery.

## Handle JSON and process status

stdout contains one JSON response; stderr contains diagnostics and progress. Inspect `ok`, then the command-specific fields in `data`.

| Result | Next action |
| --- | --- |
| Ready query with `data.results` | Select relevant results and read them with `get`. |
| `ok: true`, `data.state: "preparing"`, exit `1` | Check model state, wait with `lore model load`, then retry the same query. |
| Ready query with an empty `results` array | Check installed Packs and refine the task description if useful. |
| Accepted index operation | Follow its operation ID until it is ready or failed. |
| `ok: false`, exit `2` | Inspect `error.code` and follow [Troubleshooting](./troubleshooting). |

Semantic query is the default. A failed semantic query does not mean that relevant guidance is absent. Use keyword mode only for an intentional offline lookup or to isolate a semantic-runtime problem, and identify that mode explicitly.

## Discover the installed contract

```sh
lore describe query
lore describe get
lore describe pack.list
lore describe index.build
```

Use these schemas for arguments, fields, errors, and exit codes rather than assuming another version's behavior. Start from the [CLI reference](./cli) or [documentation overview](./index.md) for further guidance.

# 这里的“自学习”是什么，能做到什么程度？

> 面向希望理解方案、但不需要阅读检索公式的读者。本文根据 2026 年 10 月 3 日的《角色对齐检索与受控学习验证路线》整理，于 2026 年 10 月 6 日编写。它解释研究设想，不是已上线功能说明，也不新增产品承诺；实现状态以原研究文档的记录为准。

## 先说结论

这份方案里的“自学习”，更准确地说是**受控的检索策略学习**：系统从经过审核的反馈中，尝试学会更准确地理解任务、更合理地排列知识；改进先在离线环境验证，通过后才由人批准上线。

它不意味着系统每收到一个问题就自动更新自己，也不意味着知识库越大，检索就一定越准。即使后续实验成功，首轮考虑的学习范围也很小：**改进任务角色识别，或改进受约束的排序融合策略，而不是训练整个大模型、自动改写知识库或自主发布。**

理解这件事，需要分清三个层次：能自动分析问题，不等于会从反馈中学习；能做出候选新版本，不等于可以自动上线；有研究路线，不等于能力已经实现。

## 1. 为什么需要学习：找到“相关的”，还不够

Lorelum 检索的是工程知识。这里把一条知识称为 Practice，把一组知识称为 Pack。检索不仅要找到主题相近的内容，还要判断它是否适合当前任务。

下面是一个说明性例子，不是已有实验结果：

> “准备发布新版本，想先检查发布风险；现在还没有线上故障。”

“发布前检查”和“发布后故障排查”都与发布有关，但当前需要的是前者。如果系统只抓住“发布”“风险”等主题，仍可能把后者排在前面。

因此，方案先研究如何保留问题中的任务信息：现在要做什么、处于哪个阶段、处理什么对象、有哪些必要条件，以及技术背景是什么。这里的“角色”指这些信息在任务中的作用，**不是用户的职位或身份**。

学习的潜在价值，是从可信纠错中改进这种区分能力。例如，逐渐更可靠地识别“还没有故障”是影响适用性的条件，而不是可以忽略的背景。

## 2. 具体学什么：理解任务，或调整排序方式

研究文档限定了两类可学习候选。它们是待评估的方向，并不意味着两类都必须实现。

### 第一类：更准确地识别任务角色

系统需要把一句自然语言拆成有用的任务信息。例如，上面的例子可以理解为：

- 当前动作：检查发布风险。
- 当前阶段：发布之前。
- 处理对象：待发布的新版本。
- 关键条件：尚未发生线上故障。

学习可能帮助系统减少误读、漏掉条件或混淆事件先后的情况。但它不能凭空补出用户没说的目标和状态；信息不够时，应保留不确定性，并使用预先规定的回退路径。

**自动角色分析本身不是自学习。** 一个固定的分析器也能自动处理每次请求。只有利用新的可信反馈，形成并验证新的识别策略，才属于这里讨论的学习。

### 第二类：更合理地综合排序证据

即使任务已经读懂，系统仍要决定哪些知识更适用。它需要综合任务动作、阶段、条件与知识内容之间的匹配证据。

学习可能调整一个小型策略，让这些证据的组合更合理。例如，某些任务中，“当前阶段是否匹配”可能比宽泛的主题相似更重要。这只是解释方向，不是已确定或已验证的权重公式。

原方案仍限定排序依据为向量相似度证据、融合权重非负；不是引入一个不受约束、任意决定结果的学习器。目标是学到**能跨知识条目和 Pack 使用的共享规则**，而不是记住“遇到这个问题，就把某个固定 ID 排第一”。

## 3. 用什么来学：有理由的反馈，而不是把行为当答案

最有价值的材料，是明确纠错和带理由的比较。例如：

> “对于这个任务，A 比 B 更适用。A 讲的是发布前的检查，B 讲的是故障发生后的处理，而用户明确说现在没有故障。”

这类反馈既指出结果，也说明判断依据，才有机会帮助系统学到可复用的区别。

点击、曝光和 Agent 采用记录可以参考，但原方案只把它们当作弱观察：

| 观察到的现象 | 为什么不能直接当正确答案 |
| --- | --- |
| 用户点击了某条知识 | 可能只是想确认它是否有用，不代表它真的适用 |
| Agent 采用了某条知识 | 采用本身也可能是错误决定 |
| 某条知识没有被采用 | 可能没被看到，或者任务中途改变，不能直接判为负例 |
| 模型认为自己的推荐正确 | 不能把模型自己的判断回灌成标准答案 |
| 新增了很多知识内容 | 内容增加了，但没有说明哪些任务该用哪些内容，不等于增加了训练真值 |

因此，**使用次数、日志数量和知识库规模，都不能单独证明系统正在学得更好。**

反馈如何收集、由谁审核、保存多久、是否允许上传，都还需要独立设计。原方案没有默认上传或提交检索日志，也没有授权把所有用户行为自动用于训练。

## 4. 能自动到什么程度：可以研究自动改进，但发布权仍在人手里

原文提出的受控学习流程是：

```text
经审核的反馈
    ↓
去重、按来源和任务类型分组
    ↓
离线生成候选策略
    ↓
检查旧任务、新任务、未参与训练的 Pack，以及运行成本
    ↓
人工批准候选版本
    ↓
影子验证：先旁路试跑，检查实际表现
    ↓
决定发布；出现问题时可回滚
```

这个流程的关键，是把“尝试改进”和“改变正式服务”分开。一个新版本在训练样本上表现更好，不足以说明它值得上线。

从自动化边界看，可以这样理解：

| 环节 | 研究路线允许考虑的程度 |
| --- | --- |
| 每次请求分析任务 | 计划研究自动角色提取；它是学习之前的前置能力 |
| 利用反馈生成新策略 | 后续可以评估离线学习，但须先有可信反馈和获批设计 |
| 运行比较、回放和成本检查 | 是候选版本进入发布决策前的验证环节 |
| 正式服务中随时自我修改 | 不属于首轮实现范围 |
| 自动批准并发布新策略 | 不属于首轮实现范围，原路线要求人工批准 |
| 自动修改 Pack 内容 | 不属于首轮实现范围 |
| 微调整个编码模型 | 不属于首轮实现范围 |

所以，它不是一个“自己边工作边长大”的自主系统，而是一个**有反馈、有验证、有版本、有人工发布边界的改进机制**。具体训练方法、反馈产品和发布机制仍待设计，不能把流程图理解成这些设施已经存在。

## 5. 怎样证明它学到了，而不是记住了题目？

原方案希望结合几种检查，各自回答不同问题：

- **旧任务回放：** 新版本有没有把过去做对的任务做坏？
- **新任务留出：** 对没参与训练和调参的问题，是否仍有收益？
- **时间留出：** 面对后续出现的任务，是否还能保持效果？
- **未见 Pack 检验：** 换一组没参与调参的知识内容，规则是否仍然适用？
- **最差组回归：** 总体结果变好时，有没有某类任务明显退步？
- **成本检查：** 改善是否伴随不可接受的延迟、内存或计算开销？

这些检查的目的，是避免把“训练题做得更好”误认为“检索能力普遍提高”。旧样本已经被研究者看过，就不能靠重新分组伪装成独立的新测试。

即使全部通过，也只能在实际验证范围内说明新版本更合适，不能保证永不遗忘、所有领域都提升，或语料越多越准确。可回滚是风险控制，不是无风险承诺。学习也不会消除全量检索随语料增加而增长的计算量。

## 6. 研究现在走到哪一步，为什么把学习放在最后？

**按原文建立时的记录，方案 C 尚无正式实验结果，没有自动角色分析器，也没有学习器。** 这不是一份已经证明“自学习有效”的成果报告，而是一份分阶段验证计划。本文没有另行核实后续实现进展。

路线先要回答更基础的问题：

1. **先验证任务角色是否有用。** 由人工整理角色信息，检查能否改善检索。如果连人工整理都没有收益，不能指望加一个学习器解决问题。
2. **再验证文档信息和内容增长。** 检查知识侧是否提供足够证据，以及更多相近内容是否让排序变差。
3. **再验证自动分析。** 确认自动提取角色能保留可接受的收益，成本和回退行为也可接受。
4. **再做获批的产品接入。** 完成公式、接口、版本和迁移等必要设计与验证。
5. **最后评估学习的必要性。** 有可信反馈，而且学习比固定策略带来额外收益，才值得继续。

这意味着，自学习不是必做项。**如果固定策略已经足够好，或者学习没有额外收益，计划允许保留固定策略，不强行增加学习机制。**

## 7. 对外应该怎样描述这项能力？

合适的表述是：

> 我们正在研究让检索更准确地理解任务条件，并在未来利用经过审核的反馈，离线改进角色识别或小型排序策略。新版本需要通过独立验证和人工批准，才会进入正式服务。目前这仍是分阶段研究路线，不是已经上线的自动学习功能。

不宜表述为“系统越用越聪明”“会自动吸收所有用户经验”“知识越多就越准确”，或“已经可以自主进化”。这些说法超出了原方案的范围，也没有相应证据。

**最终要做到的程度，是从可信反馈中改善可复用的检索规则；不是从每一次交互中自动改写自己。是否值得做、能改善多少、能否推广到新任务和新 Pack，都还需要实验回答。**
